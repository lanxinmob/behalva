# 验收与技术验证

## 原则

不以测试数量、覆盖率数字或两名 Agent 的一句“通过”代替结果。每个测试应回答：哪个用户行为或实际故障值得验证、输入是否独立于实现假设、什么结果能揭示错误。

测试与审查均保存实际证据。代码完成、模拟验证、真实服务联调、手机实测与外部操作完成分别记录。当前逐项证据与未完成项见 [实现与验证状态](status.md)；下面是完整首版的验收要求。

## 两名独立审查者

1. 架构与可靠性审查：权限边界、状态机、数据一致性、断电或重启、审批与更新机制。
2. 产品与结果审查：完整用户流程、来源准确性、遗漏和错误匹配、手机可用性、测试是否有实际价值。

审查者独立阅读同一候选版本，给出问题位置、触发方式、影响和证据要求。修复后复核；未解决的阻断问题不算通过。争议向用户呈现，不由实现 Agent 单方面抹去。首版验收及以后每次自身代码更新都适用。

## 必须走通的流程

| 场景 | 应看到的结果 | 证据 |
|---|---|---|
| 完整机会处理 | 发现信息，检索个人材料，追问，生成表格和草稿，审批，执行，核实，归档 | 一条真实任务的逐步结果与来源 |
| 资料更新 | 修改源资料后新查询引用新版本，历史结论仍定位旧证据 | 原文变化与前后查询 |
| 跨会话成长 | 用户批准“截止不等于开始”的规则，新会话处理另一份通知正确应用 | 不同通知、规则版本、结果 |
| 隐私授权 | 未批准普通文件不进入云端请求，批准后按范围使用 | 可检查的请求边界；不泄漏凭据的日志 |
| QQ 群范围 | 仅授权群纳入处理，撤销后停止新增但仍能查旧资料 | 授权变化及接入记录 |
| 筛选质量 | 能找到用户认为有用的消息，观察漏报、重复提醒及费用 | 独立标注样本和被过滤消息抽查 |
| 手机离线 | 看缓存、改草稿、暂存任务；重连后同步且不重复创建 | 真机断网与恢复记录 |
| 编辑冲突 | 手机与后台改同一草稿时保留两版并让用户选择 | 冲突现场与选择结果 |
| 锁屏通知 | 在目标手机锁屏、外网条件下取得通知，默认内容不泄露事项 | 真机结果与必要权限 |
| 浏览器接手 | 手机接手同一会话完成用户步骤，自动化暂停且能安全交回 | 同一任务的控制权与页面状态 |
| 审批变化 | 已批准正文、附件、收件人或字段改变后阻止执行 | 实际差异与被拒执行结果 |
| 未知执行结果 | 外部操作可能成功而响应丢失时先核验，不能盲重试 | 故障注入与操作次数证据 |
| 进程恢复 | 任务中途重启后恢复等待和执行状态，不重放已完成副作用 | 持久记录和重启结果 |
| 自修改 | 独立开发、双审查、人工确认、启用与回退完整完成 | 候选提交、报告、批准和运行版本 |
| 备份恢复 | SQLite、附件与规则能恢复为可用且一致的个人工作区 | 恢复到独立目录后的实际读取 |
| 通用性 | 使用虚构的非升学目标完成资料检索与草稿审批 | 无私人背景硬编码的另一条任务 |

真实发信与提交必须使用用户明确批准的目标与内容。测试不会为了制造证据而发送无意义邮件或真实报名。结果不明故障可以在可控测试端验证，再结合真实服务联调，分别声明覆盖边界。

## 实现前的技术验证

- NapCat：日常账号登录与并用行为、指定群消息、附件、历史范围、重连与缺口。
- 手机连接：本机后台服务、WSL2 与 Windows 连接、外网 VPN、锁屏通知和分享导入。
- 浏览器接手：手机控制本机同一会话、输入与验证码、自动化控制权交接。
- 模型：实际可用服务和模型名、工具调用、流式输出、用量与失败恢复；别名不当作已确认 API 型号。
- 文档：中文资料检索、源码定位、PDF 与截图解析、增量发现成本；使用用户允许的少量代表性文件。
- SQLite：代表性导入和并发任务的写入延迟、恢复与备份；在结果显示瓶颈前不引入更重数据库。
- 网页与 Gmail：登录、读取、草稿、确认发送与结果查询；具体报名网站以可访问页面验证，不能保证未来所有站点通用。

这些问题要通过原型和测量解决，不要求用户回答实现细节。若验证失败，说明影响与替代方案，由用户决定涉及产品范围的取舍。

## 分步交付

1. 核对本草案并完成关键接入验证。
2. 完成持久任务、权限、资料引用和 App 基础同步的一条可运行路径。
3. 连通来源筛选、四表、材料、审批、邮件与已验证表单，进行真机验收。
4. 加入规则成长和受控自修改，验证双审查、更新与恢复。
5. 两名开发者 Agent 进行整体验收，修复并复核；最终展示所有已完成和未完成项。

以上是实现顺序，第一版最终验收仍覆盖用户要求的完整功能，不把某个中间阶段称为首版交付完成。
