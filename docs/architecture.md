# 架构草案

## 核心选择

SQLite 作为首版持久化数据库。目标是单人、单个权威服务实例、适量并发任务。迁移到单台服务器本身不要求更换数据库；出现多实例并发写入或实际瓶颈时再评估 PostgreSQL。

SQLite 官方说明支持应用服务器在服务内协调数据库访问；WAL 支持读写并发，但仍只有一个写入者，且不适用于跨机器共享数据库文件。

参考：
- https://www.sqlite.org/whentouse.html
- https://www.sqlite.org/wal.html
- https://www.sqlite.org/backup.html

## 模块分工

| 模块 | 职责 |
|---|---|
| C++ 后台核心 | 任务状态机、调度、权限、资料版本、模型调用编排、审批、预算、同步 API |
| SQLite | 来源、版本、可重建检索索引、任务与执行记录、审批、用量、同步事件 |
| 文件存储 | 网页快照、附件、截图、被引用证据；以内容摘要去重并由元数据关联 |
| 可读文件与私人 Git | 个人档案、规则、技能、记忆和工作流的文本版本 |
| 来源适配进程 | 文件发现、QQ、GitHub、网页登录读取、微信导入和文档解析 |
| Kotlin App | 工作台、离线缓存、草稿编辑、审批、分享导入、通知、浏览器接手 |
| 更新管理组件 | 独立构建、审查证据、人工批准、启用、健康检查和回退 |

首版采用模块化的单个核心服务，配少量必要工具进程。成熟组件可以使用其他语言。外部工具提交结构化结果，由核心服务持久化和执行权限检查，不获得任意数据库写入权限。

代码仓库保留在 D 盘；核心、SQLite、调度与索引部署在 WSL2 的 Linux 本地文件系统。Windows 专用浏览器适配器保留已有登录会话，通过 HTTPS 连接核心。本机资料经 `/mnt/c`、`/mnt/d` 读取。Linux 用户 systemd 服务配合独立的 Windows 登录启动进程保持 WSL 运行，不依赖对话窗口或终端标签页；关闭电脑、休眠和尚未登录时不能提供在线服务。迁移、验证和回退步骤见 [WSL2 部署](wsl2.md)。QQ、手机外网与锁屏仍需分别验证，不能由本机启动成功推断它们可用。

## SQLite 使用约束

- 数据库由权威后台服务拥有；耗时网络请求、模型生成与文档解析不占用写事务。
- 使用短事务和统一写入队列，评估 WAL 与持久化设置；审批和执行记录要求可靠落盘。
- 数据库位于拥有它的运行环境的本地文件系统。Windows、WSL 与手机不共享打开同一个数据库文件。
- 手机拥有独立的本地数据库，通过带版本号的 API 同步。任务重复提交使用稳定请求标识；草稿更新携带基准版本，冲突保留两份供用户选择。
- 使用一致性备份接口，配套备份附件清单和必要对象；验证恢复结果，不对正在运行的数据库仅复制主文件。
- 建表迁移具备版本号与恢复方案。附件先可靠保存后登记引用，异常留下的未引用对象可后续清理。

## 可读性与检索

个人档案、规则和技能的批准版本保持人可读。用户直接编辑受管理文本文件属于明确编辑输入，系统校验格式、记录变更并更新派生索引。助手自行提出的规则保存为候选，不因写入文件就生效。

每类数据指定权威来源：任务和审批以数据库为准；规则文本以批准版本为准；全文检索与向量等均为派生数据。避免两份独立可写的事实来源静默漂移。

先验证本地中文检索、结构化过滤、原文定位和增量更新；根据真实查询判断是否加入本地语义检索。未授权内容不送云端 embedding 或重排。索引命中后仍检查来源权限、版本与覆盖范围。

引用包含稳定来源标识、文件位置或 URL、版本、定位信息和取得时间。时间事实分别记录发布日期、报名截止、活动开始、入学年份，保留原文与不确定性。历史规律不能伪装为当年政策。

## QQ 筛选

按批准群先做授权过滤，再做持久化与候选提取；不把未批准群的正文写入工作日志或模型上下文。使用消息标识去重，关联回复、转发链和附件。

本地按来源、目标、时间和消息结构生成候选；保留上下文，重要公告和不确定项进入候选，避免纯关键词过滤造成不可观察的漏报。较便宜模型批量提取事实与相关性，关键结论回查原文或官网。

在有限窗口内抽查被过滤内容，用用户标注的有用信息评估漏报、成本和提醒负担。未授权历史范围不自动扩展。断线重连后尝试补齐并去重，无法补齐时显示缺口。

NapCat 作为候选 OneBot 接入模块，不固化到业务逻辑中。使用日常账号的兼容性、历史可取范围、附件取得和重连行为须实测。

参考：
- https://napneko.github.io/guide/napcat
- https://napneko.github.io/onebot/api

## 模型接入

参考 CC Switch 的供应商配置和协议适配思路；内部表示消息、工具调用、附件、流式事件和用量，再按协议适配。模型名和服务地址为配置，保留真实上游名称，不假定用户口中的别名就是可调用 ID。

分别核验 OpenAI Responses、Chat Completions 以及其他计划支持协议的能力。未测协议显示未验证；缺少工具调用或图片能力时明确拒绝或降级，不静默丢字段。

协议请求失败的重试与工具副作用分离。换模型、重连或重新生成不能导致已批准操作重复执行。用量缺失按未知或估计记录，不能记为零成本。

参考：https://github.com/farion1231/cc-switch

## 执行与审批

任务、步骤和外部操作分开保存状态。任务可以等待资料授权、追问、用户接手、最终审批或结果核实；等待期间释放工作资源。进程重启恢复持久状态，不重新生成并执行整个任务。

审批对象包含目标、账号、收件人、正文、实际附件摘要、表单字段、动作类型和内容版本。执行前重新校验；内容或附件改变则要求重新审批。自然语言同意应在明确的待审批对象上解析，群消息和网页不能产生批准。

外部操作至少区分准备、待批准、执行中、成功、明确失败、结果未知。发送或提交后连接中断，先查已发送邮件、回执和申请状态；结果未知时停止自动重试。数据库事务不能保证外部站点恰好执行一次。

App 接手同一浏览器会话时，自动化暂停，持有明确控制权；交回后重读页面状态，防止与用户并行点击。验证码由用户处理，不绕过。只能对已验证的站点流程声明支持。

## 手机与同步

首次设备配对建立访问权限；使用加密连接，支持撤销设备。网络方案从用户接受的 VPN 或内网穿透中验证选择，数据库不暴露给手机。

服务端按同步游标提供任务、表格和草稿变更，附件按用户选择缓存。离线新任务保存在待发送队列；离线审批在重连后仍须校验对象版本，不能批准已过时内容。

系统推送只携带最少事件信息，锁屏显示“助手有新消息”；详细内容连接核心服务获取。通知不是任务记录的权威来源，App 打开后同步补齐。手机厂商通道可用性、后台权限与 VPN 组合必须在真机验证。

## 自修改和恢复

运行版本与开发工作树隔离。开发和审查进程不能自行批准新代码启用，不能通过新代码修改现行批准结果。审查证据绑定候选提交和构建产物。

两名审查 Agent 独立判断：一名侧重架构、权限、数据与恢复，一名侧重用户流程、实际正确性、检索和测试质量。无有效审查结果不自动视为通过。

用户批准后由更新管理组件执行切换；记录运行版本，做健康检查并提供回退。数据库迁移若不兼容旧版本，先给出独立的数据恢复方案，不能只承诺切换二进制。
